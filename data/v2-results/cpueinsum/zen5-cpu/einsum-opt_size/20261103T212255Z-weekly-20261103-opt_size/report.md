## What was measured

- **Workload** — One whole einsum per instance, from the `tenferro-einsum-benchmark` problem set: pairwise matrix products, batched and elementwise products, outer products, a matrix-chain problem, MPS inner products, two MERA networks, two tensor-network permutation problems, and two likelihood contractions of 38 and 84 operands. The operands are generated by the harness (deterministic, dtype-templated) and the contraction order is taken from the corpus's own `paths` entry, so the rows measure one library against two declared schedules, not two libraries.
  Source: The corpus is `tenferro-einsum-benchmark` `data/instances/*.json` at the revision in `pins/tenferro-einsum-benchmark.rev`, materialised by `scripts/setup_extern_deps.sh`. Each instance declares `name`, `format_string`, `shapes`, `dtype` and two opt_einsum-style positional paths; `crates/cpueinsum-bench/src/corpus.rs` in the measured revision translates them into cpueinsum's integer-label, SSA-order API.
  Known blind spot: The corpus instance `str_mps_varying_inner_product_200` is **not declared**: the harness's own cross-row verification refuses it (`MISMATCH(opt_flops) rel_err=NaN`, exit 1) at every declared thread budget. It is therefore not measured, not skipped, and not part of this suite's coverage; the evidence is in `docs/verify-refusal-str_mps-varying-inner-product-200.md`.
  Known blind spot: The declared identity is the numeric sentinel `n = 1`: every instance has fixed extents, so the declaration grid has one shape and the real operand shapes are the harness's `case_m` (operand count), `case_n` (total input elements) and `case_k` (output elements) columns, not geometry the toolkit compares.
  Known blind spot: The engine rows are two contraction orders of the same library, so a row here is a schedule comparison inside cpueinsum, not a comparison against an independent implementation; there is no reference engine and no vendor arm in the first record.
  Known blind spot: Every instance has unit batch, so a cost proportional to batch elements is invisible.
  Known blind spot: One size per instance: a ratio here says nothing about a neighbouring instance, and the set is not a sweep.
  Known blind spot: A corpus revision is not one of the measured repository's `invalidated_by` paths: the declaration records the corpus pin it was generated from, and a corpus bump has to be a deliberate regeneration of this suite.
- **Rows** — one row per engine in every table below:
  - `opt_size` — cpueinsum executing the corpus's `paths.opt_size` order: the order the corpus declares as minimizing the largest intermediate (memory).
    Identity: the measured cpueinsum-rs revision in this run's manifest (`library.commit`), pinned by `pins/cpueinsum-rs.rev`
    Caveat: The order is the caller's, taken verbatim from the corpus; no order is searched or corrected here.
    As measured: `cpueinsum` (the provider in the measured revision; see library above)
